# CANONICAL DATA MODEL

## Purpose

This document defines the canonical data model for WorkCaptain / ProWork.

The canonical data model turns the institutional system into governed application data structures that can be implemented consistently across UI, services, APIs, automation, evidence, and certification surfaces.

## Model Principle

The data model must not be feature-first.
It must be institution-first.

Every canonical object must remain compatible with:

- truth integrity
- governance integrity
- allocation integrity
- resilience integrity
- disclosure integrity
- engagement integrity
- doctrine integrity
- federation integrity
- accountability integrity
- closure integrity

## Canonical Object Families

The canonical data model must support at minimum:

1. identity and authority objects
2. intake and pipeline objects
3. portfolio and command objects
4. allocation and resilience objects
5. assurance and certification objects
6. accountability and remediation objects
7. federation and entity objects
8. evidence and invalidity objects

## Canonical Object Requirements

Every canonical object must define:

- canonical identifier
- object purpose
- ownership boundary
- state model
- upstream dependency set
- permitted transitions
- evidence linkage
- invalidity hooks
- visibility boundary
- escalation boundary

## Model Rule

No canonical object may exist in implementation as a free-form record that bypasses governed lifecycle or governed authority rules.

## Outcome

The canonical data model becomes the structural source of truth for implementation-ready product objects.
